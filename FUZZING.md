# Fuzzing

VAL-005 makes a v1.0.0 release conditional on the fuzz targets having
accumulated **at least 10 million executions with no crashers**. This file
records the run that satisfies it, what the committed corpus is, and how to
repeat both.

## Targets

Three targets in `fuzz_test.go`, chosen because each one parses attacker-shaped
input into a fixed-size structure and each one has a different failure mode:

| target | input | what a crash would mean |
|---|---|---|
| `FuzzParseRecord` | a whole log file, any format | the framing or a field scanner walked off a buffer |
| `FuzzPrefixTemplate` | a `log_line_prefix` plus a line | the prefix compiler accepted a template it cannot match |
| `FuzzUnquote` | one quoted field | `AppendUnquoted` mis-sized its output |

Each target asserts more than "did not panic", because a parser that silently
dropped every record would pass that bar:

- `FuzzParseRecord` reads every borrowed field of every record it produces and
  clones it, so a scanner that returned a slice longer than its backing array
  is caught rather than merely survived; it requires `Raw` never to exceed the
  input, offsets never to go negative, and `Err` to stay nil for every input
  except an invalid `LinePrefix`, which is a configuration mistake and
  deliberately fatal.
- `FuzzPrefixTemplate` requires a compiled template to round-trip its own
  source, since `DetectedPrefix` reports it to the caller, and requires the
  unmatched remainder never to be longer than the line it came from.
- `FuzzUnquote` requires the unquoted result never to exceed the input, since
  no escape expands, and requires appending never to disturb bytes already in
  the destination.

## The VAL-005 run

| item | value |
|---|---|
| date | 2026-09-01 |
| machine | AMD Ryzen 9 7940HS, 8 physical / 16 logical cores, windows/amd64 |
| Go | 1.26.5 |
| command | `go test -run '^$' -fuzz <target> -fuzztime 10000000x .` |

| target | executions | crashers | new interesting inputs |
|---|---:|---:|---:|
| `FuzzParseRecord` | 10 000 000 | 0 | 469 |
| `FuzzPrefixTemplate` | 10 000 000 | 0 | 68 |
| `FuzzUnquote` | 10 000 020 | 0 | 13 |
| **total** | **30 000 020** | **0** | **550** |

Three times VAL-005's floor, with nothing found. The count is exact rather than
"about 10 million" because `-fuzztime` accepts an execution count with an `x`
suffix, which is the form worth using for a threshold stated in executions: a
wall-clock budget measures the machine, not the requirement.

## The corpus is not committed

The run above left 1 132 coverage-guided inputs in Go's build cache under
`$(go env GOCACHE)/fuzz/github.com/cybertec-postgresql/pglogwatch/`. They are
deliberately **not** in this repository.

Committing them would put them under `testdata/fuzz/<Target>/`, where Go
replays them as seed corpus on every plain `go test`. That is a real benefit --
a path some mutation found would be re-checked on every run -- and it costs
1.6 MB across 1 132 opaque files whose names carry no meaning and whose
contents nobody reviews. The same trade DAT-001 already settled for the
benchmark corpus applies here: the manifest is worth committing, the generated
payload is not.

So the corpus is a local artefact, regenerated by re-running the targets. What
this file records -- the execution count, the absence of crashers, and the
machine -- is the part a release needs.

`.gitignore` ignores `/testdata/fuzz/` for the related reason: what the fuzzer
writes there is a *crasher*, an input that just failed, and a failing run must
not leave a staged file behind for somebody to commit without reading it. A
crasher should be read, minimised, and added to `fuzz_test.go` as a named seed
recording the bug it found.

## Repeating it

```bash
# The VAL-005 run: exact execution counts, roughly five minutes in total.
for t in FuzzParseRecord FuzzPrefixTemplate FuzzUnquote; do
  go test -run '^$' -fuzz "$t" -fuzztime 10000000x .
done
```

`task fuzz` is the short form -- 30 s per target -- and is what to run before a
commit. The 10-million run is a release gate, not a pre-commit check.

Anything the fuzzer finds is written to `testdata/fuzz/<Target>/` and printed.
Reproduce it with `go test -run 'FuzzParseRecord/<name>' .`.
